Research brief

What the reference course actually teaches

Before designing anything, I looked at what IndyDevDan — an independent engineer-educator with 15+ years of production experience and a YouTube channel built around Claude Code and agentic workflows — actually ships across his two paid courses, Principled AI Coding (the prerequisite) and Tactical Agentic Coding (the advanced course it feeds into).

Findings, official source only — re-verified against the live pages

Shape
Principled AI Coding: 8 lessons, ~6 hrs. Tactical Agentic Coding: 14 lessons (an 8-lesson core + a 6-lesson "Agentic Horizon" extension), ~6.5 hrs. Combined: 22 lessons, ~12.5 hrs.
Core framework
Two frameworks, one lineage: Principled AI Coding teaches the "Big Three" — Context, Prompt, Model. Tactical Agentic Coding upgrades this to the "Core Four" by adding a fourth lever, Tools.
Signature ideas
The 12 Leverage Points; AFK Agents (via a "PITER" framework); Closed Loop Prompts (self-correcting agents with strategic feedback loops); ADWs — AI Developer Workflows (deterministic code composed with non-deterministic agents); "The Agentic Layer" ("the one meta-tactic to rule them all"); multi-agent orchestration via a dedicated Orchestrator Agent; Zero-Touch Engineering (ZTE) as the stated end-state, "where your codebase ships itself."
Gate
Explicitly built for "the top 20% of engineers" and "NOT for beginners" — required fluency includes Git, GitHub CLI, Node 18+, Python 3.10+, and existing test/build tooling.
Philosophy
Durable principles over any specific model, tool, or agent — "using the best tool for the job" rather than chasing whichever is newest.

Everything above is publicly described on the creator's own site — I did not access, purchase, or reproduce any paid lesson content. Several search results were course-piracy resale sites; those are excluded on purpose. Revision note: an earlier draft of this brief mislabeled Tactical Agentic Coding's framework as "The Big Three" and undercounted the combined lesson total — both are corrected above after re-checking the source pages directly.

Design rationale

What's borrowed, what's original

The reference course's pedagogical shape is worth keeping: a hard skill gate, a small set of named principles taught before any tool, a progression from concrete to autonomous, and a capstone that has to run on real code, not a toy. That shape is sound regardless of who teaches it.

What follows below does not reuse his proprietary terms or lesson content. It's a separate curriculum, "Agent Operations," with its own framework and module set, aimed at the same transition — engineer to agent operator — built from first principles rather than from his course transcript.

Core framework

The Four Dials

Every lesson in this curriculum comes back to one of four things an operator adjusts. Nothing else is tunable — an agent that's failing is failing because one of these four is wrong.

F

Feed

What the agent can see: files, docs, prior runs, constraints. Most failures are starvation, not stupidity.

F

Frame

The spec you hand it: scope, done-criteria, and what's explicitly out of bounds.

F

Fit

Which model and which tools for this task — not the biggest, the right one.

C

Check

How the work is verified before a human ever looks at it — tests, lint, a second agent, a rubric.

Technical grounding

Where the Four Dials come from in the literature

The Four Dials are original to this curriculum, not IndyDevDan's terms — but they're not invented from nothing either. Each names something with prior art in agent research, added here from my own technical background rather than from the reference course.

Grounding, by dial

Feed
Relevant-information placement, not just presence, measurably changes model performance — accuracy drops when the needed fact sits in the middle of a long context instead of at the start or end. This is why file selection beats prompt length: it's a placement problem as much as a content one. Liu et al., 2023 — "Lost in the Middle" (arXiv:2307.03172).
The loop itself (Tiers 0–1)
The plan → act → observe cycle this course assumes from the start is the same loop formalized as interleaving reasoning traces with actions and tool observations, letting the agent correct course mid-task instead of committing to a single plan upfront. Yao et al., 2022 — "ReAct: Synergizing Reasoning and Acting in Language Models" (arXiv:2210.03629).
Check + Tier 3 orchestration
The self-check loop in Module 2.3 and the fan-out/fan-in pattern in Module 3.3 correspond to named patterns in Anthropic's own applied engineering guidance — "evaluator-optimizer" and "orchestrator-workers" — from a write-up on which agent patterns hold up in production versus which just look good in a demo. Anthropic, 2024 — "Building Effective Agents".
Frame and Fit
No single paper anchors these two — they're closer to existing software-engineering discipline (testable specs, cost-aware tool selection) applied to agent delegation, not a novel research claim. Flagged here rather than papering over the gap with a citation that doesn't quite fit.

Entry gate

Who this is for

Same bar as the reference course, for the same reason: teaching delegation to someone who can't yet do the work themselves produces engineers who trust agents they can't evaluate. Prerequisites: 2+ years shipping production code, comfortable in a shell, has used any AI coding tool at least casually, owns a real codebase (personal or work) to run the capstone against.

Curriculum

Four tiers, eleven modules

Tier 0

Orientation

One module. The mindset shift, before any tooling — most people skip this and pay for it in Tier 2.

0.1

You Are No Longer the Typist

Lecture · 25 min

Reframes the job: from producing code to producing the conditions under which an agent produces correct code. Covers why "just prompt better" plateaus, and what replaces it.

Read the lesson

For most of software history, your value was measured in code you produced: lines shipped, tickets closed, PRs merged. That's ending — not because code stops mattering, but because you stop being the one who types it. Your value moves upstream, into four decisions that determine whether an agent's code is any good. This course calls them the Four Dials: what the agent can see (Feed), what you've told it to do and when to stop (Frame), which model and tools you handed it (Fit), and how the work gets checked before you look at it (Check). An agent that fails is failing because exactly one of these is wrong — never because it's "not smart enough." Diagnosing which dial is off is the entire skill. The trap: "just prompt better" plateaus fast, because a better sentence can't fix a starved context window, an ambiguous done-criterion, the wrong model for the job, or a missing verification step. Those are structural problems, not verbal ones.

Try it

Pull up your last five completed tickets. For each one, write one line: was the hard part typing the solution, or deciding what "correct" meant? If more than half were typing, you're still doing the job the old way.

Done when: you can name, for your last week of work, which parts were typing and which were judgment.

Tier 1 · Foundations

Running One Agent Well

Concrete, hands-on, single agent, full supervision. Every lesson ships a working artifact.

1.1

First Real Task, End to End

Lab · 45 min

Take one real (not toy) ticket from your own backlog through an agent from spec to merged diff, narrating every decision point out loud.

Read the lesson

Pick one ticket from your actual backlog — not a toy. Hand it to an agent as a real task: give it the ticket text, point it at the relevant files, and let it work through spec, implementation, and self-check without you typing any code yourself. Your job for this lab is narration, not intervention: at every point where you're tempted to jump in, stop and write down what you were about to do and why.

Worked example — a real correction log, from a raspberry-pi virus-scan script that needed a check for an overlapping backup job:

  1. Wrote the conditional (flock -n -x ... || echo HELD) — typing.
  2. Decided the check must run before the scan, not after — judgment (changes what the check is even for).
  3. Chose a non-blocking lock probe over inspecting the backup process directly — judgment (the wrong tool here could hang the scan).
  4. Tested the logic against both a free and a held lock before touching the real script — judgment (proof before production).
  5. Backed up the original script and diffed before/after installing — judgment (reversibility).
  6. Decided to surface the note in the existing log field rather than add a new one — judgment (schema stability over completeness).

Six moves, one of them typing. That ratio is what you're measuring.

Try it

Run the exercise. When you're done, count your own moves the same way — typing vs. judgment — and keep the log. You'll use it again in Tier 3.

Artifact: a merged PR plus a one-page log of every correction you made and why.

1.2

Feed and Frame

Lecture + Lab · 60 min

The first two dials in depth: what context actually moves the needle (file selection beats prompt length), and how to write a frame with unambiguous done-criteria.

Read the lesson

Feed is what the agent can actually see: the files you pointed it at, the docs it can reach, the constraints you stated out loud. Most agent failures that look like "it's not smart enough" are actually starvation — the answer was in a file three directories over that nobody mentioned. File selection beats prompt length; a precise pointer to the right 200 lines outperforms a paragraph of context about the whole system.

Frame is the spec you hand it: scope (what's in, what's explicitly out), and done-criteria specific enough that two different people would agree on whether it's met. "Make the tests pass" is a frame. "Make it better" is not — there's no way to fail at "better," which means there's no way to check it either.

A usable frame template has three lines: (1) the one thing that must be true when this is done, (2) the files or systems this may NOT touch, (3) how you'll verify it without re-reading the whole diff yourself.

Try it

Write that three-line frame for a task you're about to hand off — before you hand it off, not after. Save the template; Tier 2 builds directly on it.

Artifact: a reusable task-frame template you'll use for the rest of the course.

1.3

Reading a Failure

Lab · 40 min

A catalog of the five ways agent output fails silently — confident wrong answers, scope creep, invisible assumptions, stale context, and over-eager cleanup — with a diagnostic pass for each.

Read the lesson

Five ways agent output fails silently, in the order you'll meet them:

  1. Confident wrong answer — states something false with the same tone as something true. No hedge to catch.
  2. Scope creep — solves the ticket plus three adjacent things nobody asked for, burying the actual fix in unrelated churn.
  3. Invisible assumption — picks a default (a timezone, a null-handling rule, an API version) and never says so.
  4. Stale context — reasons from a file version, a schema, or a conversation state that's since changed.
  5. Over-eager cleanup — "while I was in there" edits: renamed variables, reformatted files, removed "unused" code that wasn't unused.

Each has a fast tell. Confident-wrong: cross-check the one claim that would be expensive if false. Scope creep: diff the file list against the frame's "must not touch" line. Invisible assumption: grep the diff for any literal that isn't in the spec (a date, a magic number, a hardcoded string). Stale context: check the timestamp of the last file read against the timestamp of the last relevant edit. Over-eager cleanup: read the diff stat before the diff — a 40-line fix with a 400-line diff is the tell by itself.

Try it

Take a diff you didn't review carefully at the time — yours or a teammate's. Name which of the five it is, in under a minute, before reading further into it.

Done when: given a broken diff you've never seen, you can name which of the five it is in under a minute.

Tier 2 · Practice

Making the Agent Check Itself

Specs, verification loops, and tool access — the agent starts doing more without you watching every step.

2.1

Spec Before Code

Lecture + Lab · 50 min

Writing a spec the agent can be graded against — testable invariants, not vibes — and using it as the frame for a multi-file change.

Read the lesson

A spec the agent can be graded against reads like a test file in prose: a numbered list of invariants, each one a statement that's either true or false of the finished code — never a vibe. "Handles errors gracefully" is not an invariant. "Returns a 422 with a field-level message when the payload is missing a required key" is.

Write the spec before any code exists, covering the obvious path plus at least three non-obvious edge cases (the empty case, the concurrent case, and the malformed-input case are a reliable starting three). Hand the spec to the agent as the Frame, and hold the finished implementation against it line by line — an invariant either has code that satisfies it or it doesn't; there's no partial credit to negotiate.

Try it

Write a spec with 3+ non-obvious edge cases for a real feature, then implement against it. Check the implementation against the spec yourself before you check it against anything else.

Artifact: a spec + implementation for a feature with 3+ non-obvious edge cases.

2.2

The Fit Dial

Lecture · 35 min

Model and tool selection as a real engineering decision: cost, latency, and failure-mode tradeoffs across a cheap/fast model, a strong reasoner, and a specialized tool call.

Read the lesson

Fit is model and tool selection, and it's a real engineering tradeoff, not a default you leave on autopilot. Three tiers to reason about: a cheap/fast model for high-volume, low-stakes, well-specified work (formatting, simple lookups, mechanical edits); a strong reasoner for ambiguous, high-stakes, or architecturally consequential work (anything where a wrong call is expensive to unwind); a specialized tool call for anything with a deterministic right answer (arithmetic, a linter, a compiler, a search index) — never make a model "reason" its way to something a tool computes exactly.

The failure mode in both directions is expensive: an overpowered model on trivial work burns latency and cost for no quality gain; an underpowered model on ambiguous work produces confident mistakes (see Module 1.3) that cost more to catch than the cheap run saved.

Try it

For your next five tasks, before starting each one, say out loud which tier it is and why. If you can't justify it in one sentence, that's the tell you defaulted instead of deciding.

Done when: you can justify, in one sentence, why a task got the model it got.

2.3

Closing the Loop

Lab · 55 min

Wiring the Check dial into the workflow itself: tests-first hand-off, an agent that runs its own lint/typecheck/test cycle, and a second agent that reviews the first's diff before you do.

Read the lesson

Check is the dial most people skip because it looks like extra work — until you count the time spent manually re-verifying agent output by hand, every single time. Closing the loop means the verification is wired into the task itself, not bolted on after: a tests-first hand-off (the agent gets the spec's tests before it writes the implementation, so it has something to run against, not just something to satisfy from description), the agent running its own lint/typecheck/test cycle before it hands the diff back to you, and — where the stakes justify it — a second agent reviewing the first's diff against the spec before you ever open it.

The bar for this module: a task completes with zero manual test-running on your part. Not zero verification — zero manual verification. The checking still happens; it just doesn't require your hands.

Try it

Take a task you'd normally verify by hand and wire the check into the handoff instead — tests the agent runs itself, or a second agent reviewing against the spec. Confirm the check actually caught something once, even a small thing, before you trust the pattern.

Artifact: a task that completes with zero manual test-running on your part.

Tier 3 · Autonomy

Running the Fleet

Standards encoded as artifacts, agents running without a babysitter, and more than one agent at a time.

3.1

Encode, Don't Repeat

Lab · 45 min

Turning the corrections you've been making by hand since Tier 1 into a standing artifact — a house style doc, a reusable reviewer persona, a lint rule — so the agent stops making the same mistake.

Read the lesson

By Tier 3 you've made the same correction more than once — a formatting preference, a "don't do X, we tried it and Y happened" rule, a house style for error messages. Each repeat is a signal that the correction belongs in a standing artifact instead of your head: a style doc the agent reads before it starts, a reusable reviewer persona that checks for exactly that class of mistake, a lint rule that fails the build before a human ever sees the diff.

The test for whether something's worth encoding: would you make this same correction on the next five similar tasks if you didn't write it down? If yes, write it down once, in the place the agent actually reads, and stop making it by hand.

Try it

Pick one correction you've made at least twice. Encode it as a standing artifact, then run the next task through the same context and check whether the correction rate actually dropped.

Artifact: one encoded standard that measurably reduces your correction rate on the next 5 tasks.

3.2

Working Without a Babysitter

Lecture + Lab · 60 min

Designing a task an agent can run unattended: checkpoints instead of continuous supervision, a rollback path, and a hard stop condition it can't talk itself past.

Read the lesson

An unattended run needs three things a supervised one doesn't: checkpoints instead of continuous watching (specific points where you review a summary of what happened, not a live transcript), a rollback path that's cheap to execute and doesn't depend on you remembering the pre-run state, and a hard stop condition the agent can't reason its way past — a budget, a file-count limit, an explicit list of paths it may never touch, enforced structurally rather than requested politely.

Design the stop condition first. If the only thing preventing a runaway is "the agent probably won't," it's not a hard stop — it's a hope.

Try it

Design and run one task unattended: a checkpoint log, a tested rollback, and a stop condition you verify actually triggers (deliberately trip it once on a throwaway case) before you trust it on something real.

Artifact: an unattended run with a checkpoint log you review after the fact, not during.

3.3

One Operator, Several Agents

Lab · 60 min

Splitting a task across specialist agents (a finder, an implementer, a reviewer) under one orchestrator, and reading a fan-out/fan-in result without reading every sub-agent's transcript.

Read the lesson

Split a task too broad for one agent's context across specialists under one orchestrator — a finder that locates the relevant code, an implementer that changes it, a reviewer that checks the diff against the spec — and practice reading the fan-out/fan-in result at the level of the orchestrator's summary, not by opening every sub-agent's transcript.

The skill here isn't delegation — you've been doing that since Tier 1. It's trusting a synthesis enough to act on it, while still knowing which claims in that synthesis you'd actually verify if something looked off. Total trust and zero trust are both wrong; the operator's job is knowing where the line is for this specific task.

Try it

Run a 3+ agent pipeline on something genuinely too broad for one context. Before opening any sub-agent transcript, decide from the orchestrator's summary alone whether you trust the result — then spot-check exactly one claim to see if you were right to.

Artifact: a 3+ agent pipeline on a task too broad for one agent to hold in context.

3.4

Measuring the Operator, Not the Agent

Lecture · 30 min

The four numbers that tell you whether delegation is actually working, and why "lines of code shipped" isn't one of them.

Read the lesson

Four numbers tell you whether delegation is actually working — the same four the capstone rubric below grades on: human touches per cycle (how many times you had to step in), defects reaching review (mistakes that got past the agent's own checks), time from trigger to reviewable output, and whether a rollback path has ever actually been exercised, not just designed.

"Lines of code shipped" isn't one of them, on purpose — it measures the agent's output, not your operation of it. An operator whose touches-per-cycle keeps dropping while defect rate stays at zero is improving, regardless of how much code moved. One whose touches keep climbing is drifting back toward Tier 1 no matter how sophisticated the pipeline looks.

Try it

Pull your own numbers for the four metrics from your last two weeks of real work — not a class exercise, the actual job. That's your baseline; the capstone below is graded against improving it.

Done when: you have a personal baseline for all four, from your own last two weeks of work.

The Standing Pipeline

Take one recurring task from your actual job — not invented for class — and build a pipeline that runs it with minimal touch: spec template, model/tool selection, a self-check loop, an encoded standard, and a rollback path. Run it for two real cycles before presenting.

Reviewed against the rubric below by a peer who has never seen the pipeline before — if they can't tell what it did without asking you, it's not done.
